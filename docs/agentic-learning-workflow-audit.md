# Fiosra Agentic Learning Workflow: Cross-Cutting Implementation Recommendation

**Prepared by:** Manus AI  
**Evidence baseline:** shared-repository audits of `feat/end-to-end-learning-workflow` at commit `59036e5d6fc97b42a9a23aa80736d5c6009bae8e`  
**Scope:** Issues **#40–#44**: Guided Evidence Canvas, server-authoritative learning orchestration, misconception governance, knowledge-graph utility, and the multi-provider journey harness.

## Executive decision

**A guided canvas with constrained agentic assistance fits Fiosra’s product direction, but an autonomous “agent” does not.** The appropriate product is a **student-owned, server-authoritative evidence workflow**: learners write and revise their own structured work; the system can offer bounded, reversible, section-scoped prompts; and every consequential transition is attributed, versioned, and reviewable. The model may phrase an approved instructional move. It must not decide progression, grade, diagnose a learner without bounded evidence, write into a draft, publish content, or access the Answer Vault.

The present implementation is **not yet safe to market as attributable learner work or trustworthy instructional evidence**. Its most consequential defect is shared across all five issues: client-declared identities and the generic event writer can bypass ownership, lifecycle, and provenance controls. The recommended strategy is therefore to ship a narrow, deterministic vertical slice only after embedding server-derived authorization and typed state transitions in that slice. This produces a real learner artifact and a credible foundation without prematurely expanding model authority. [1] [2] [5]

> **Decision rule:** Fiosra should invest in a constrained co-pilot only where a server can explain what it was permitted to offer, what the learner did with it, and which exact student-authored revision is being reviewed. Otherwise, the system should abstain or provide deterministic guidance.

The following are **audit findings**, not proposed designs. They describe the inspected branch and its current behavior.

## Current misconception creation: present state and required boundary

**Current state.** Misconception creation is manual seed-file editing, followed by direct PostgreSQL upsert. A seed record is therefore effectively published upon deployment. The current relational representation keeps a limited card shape—such as a KC string, domain, flawed rule, remediation hint, and vector—but discards important authoring and governance data. It has no candidate, review, published, deprecated, or retired state; no immutable version history; no accountable educator decision; and no durable provenance record. [3]

The current matcher is also unsuitable as a learner-profiling mechanism. Its 1,536-coordinate deterministic embedding is generated by hashing text rather than by a semantic embedding model. Combined with top-one same-domain matching and the low threshold, it produces a false-positive exposure that cannot be repaired by a better user interface. **Generic dialogue should remain Socratic but unlabelled** until diagnosis is restricted to an active published assignment or question, approved target KCs, and published misconception versions, with calibrated abstention for low-confidence or ambiguous inputs. [3]

**Design recommendation.** Build a versioned educator-governed state machine: `candidate → in_review → published → deprecated/retired`. Publication must require target KC(s), provenance, learner-language evidence or an approved analogue, remediation content, author, reviewer, decision rationale, effective date, and immutable version. Only published, in-effect versions pinned by a published assignment may be retrieved. Candidate-generation automation, if later introduced, may create review candidates only; it must not publish, diagnose, or expose raw student submissions to an external model. Effectiveness must be measured with a declared post-intervention KC criterion and retention evidence, not merely event counts. [3]

## Actual Neo4j value and limitations

**Verified value.** Neo4j already represents a directed acyclic prerequisite relation among a small KC catalog. Its existing traversal functions can identify direct or transitive prerequisites and can support a teacher-facing explanation. The strongest near-term use is not learner mastery prediction or autonomous sequencing. It is **prerequisite coverage before module publication**: a teacher chooses the KCs a module targets, sees prerequisite paths not covered by earlier modules or resources, and deliberately remaps, reorders, adds coverage, or records a waiver. This is an explainable curriculum decision that can justify graph maintenance cost. [4]

**Verified limitations.** The graph does not currently model courses, modules, learner mastery, evidence coverage, or misconception relationships. Its interface, filters, counts, and controls are static. Neo4j is not the system of record for the current misconception store or core tutoring decisions. The graph service’s fallback and domain normalization are unsafe, and Docker currently treats Neo4j availability as more operationally central than the product evidence supports. [4]

**Design recommendation.** Treat Neo4j as an optional traversal accelerator behind a **versioned canonical KC catalog projection**, with PostgreSQL able to return the same prerequisite-coverage explanation when Neo4j is unavailable. Normalize domains at the canonical boundary, validate all relational KC references, distinguish unavailable from empty and unseeded states, and remove or clearly label any display-only graph claims. Do not use caller-supplied mastery to gate learners or auto-advance modules. [4]

The sequence below is deliberately ordered by integrity dependency rather than by visual appeal. A canvas UI, diagnostic taxonomy, graph UX, or live provider test cannot make trustworthy claims while actor identity, session ownership, and event authority remain client-controlled.

Remove, internalize, or strictly protect generic event logging. Replace arbitrary client events with typed server-owned commands and allow-listed payloads. | Unauthorized, mismatched-actor, cross-session, unassigned-educator, unpublished-assignment, arbitrary-event, and post-submission write tests fail safely without changing state. Grades can be finalized only by an assigned educator after submission and valid rubric/grade checks. [1] [2] [3] [5] |

[1] [5] |

### Why this order is decisive

The shared foundation is not a preparatory refactor that can be deferred. It is the control plane for every later claim: student ownership in **#40**, server-authoritative workflow in **#41**, diagnostic integrity in **#42**, educator-facing curriculum decisions in **#43**, and credible end-to-end acceptance in **#44**. Once it exists, the canvas is the highest-leverage first product increment because it establishes a durable artifact that both the orchestrator and assessment pipeline can respect. [1] [2] [5]

The roadmap intentionally delays two attractive but unsafe features: autonomous planning/progression and generated edit diffs. Autonomous behavior conflicts with the desired learner-agency boundary, while diffs create provenance ambiguity unless they are anchored to exact server revisions and an explicit Accept/Edit/Dismiss lifecycle. [1] [2]

## Single first implementation slice: recommendation

**Implement one secured, server-authoritative five-section CER canvas vertical slice for issue #40, with the minimum shared #41/#44 controls embedded in its contract. Do not start with a generic agent framework, a graph visual refresh, or live generated edits.**

The slice should provide five ordered assignment-declared sections: **working claim, source observations, reasoning, alternative explanation, and revision reflection**. Public assignments must expose only the labels, guidance, ordering, required status, bounded-text policy, and permitted bounded suggestion kinds. They must not expose vault tokens, reference answers, or private teacher prompts. The server must reconstruct draft state from append-only typed events or snapshots, maintain monotonic section revisions, and reject stale writes with `409 Conflict` rather than silently overwriting work. [1]

Every source use must be a structured object linked to a published assignment source chunk and, where applicable, the selected quote/span and learner rationale. Deterministic section cards may offer only approved actions—for example, an empty-section prompt, section-specific Socratic question, neutral outline, or a previously selected source excerpt. Rendering a card cannot mutate the draft. A learner must explicitly **Accept**, **Edit before acceptance**, or **Dismiss** each offer. The resulting trace must preserve a stable suggestion ID, base/result revision, author type, source references, action outcome, and deterministic/provider metadata. [1]

The same implementation must enforce authenticated actor/session ownership, published-assignment checks, active-session lifecycle, typed allow-listed event commands, and a deterministic acceptance fixture. The fixture should create an isolated course, module, approved sources and KCs, teacher rubric/reference solution, published assignment, learner session, learner source use and help request, submission, and authorized educator review. Its negative cases must prove that no cross-learner read/write, forged provenance event, post-submission edit, vault material, or private prompt is possible. [2] [5]

This is a **single coherent slice**, not a collection of speculative infrastructure tasks: it delivers a usable learner workflow while proving the ownership, attribution, resilience, and review contracts on which every later agentic feature depends. It remains valuable if a provider is disabled because deterministic prompts and all draft actions still work. Server-generated diffs, autonomous planning, automatic section progression, taxonomy candidate generation, and learner-mastery graph decisions are explicitly out of scope until this contract passes deterministic and authorized end-to-end acceptance. [1] [2] [3] [4] [5]

## Architectural guardrails for all subsequent work

| Guardrail | Required interpretation |
|---|---|
| **Server owns truth** | Resolve actor, role, enrollment, session, assignment, question, section, lifecycle, and allowed action server-side. Treat client fields as requests to validate, not authority. |
| **Student owns authored text** | The only durable “final student work” is an explicit server-reconstructed projection of student-authored section revisions. Assistance is never silently merged into it. |
| **Assistance is bounded and reversible** | A model or deterministic rule can propose an allowed instructional move. It cannot mutate a draft, advance workflow state, grade, diagnose, publish, or retrieve private solution material. |
| **Provenance is structured** | Record stable IDs, revisions, source references, actor/author type, action outcome, and metadata required for review. Do not infer attribution from free-form chat strings. |
| **Diagnosis can abstain** | A missing, weak, unrelated, or ambiguous match produces no learner diagnostic event. Generic Socratic help remains available without a label. |
| **Neo4j is optional for core availability** | The canonical catalog and prerequisite-coverage response must stay available through a truthful PostgreSQL projection when Neo4j is unavailable. |
| **Evaluation follows contracts** | Deterministic security and state-transition assertions are release gates. Provider quality and pedagogical calibration are reported separately and do not weaken those gates. |

## Conclusion

Fiosra should proceed with the canvas/agentic direction **as a constrained learning workflow, not as an autonomous tutor**. The product opportunity is strong: a structured evidence canvas can make learner thinking, source use, revision, and bounded help visible to both students and educators. However, that opportunity depends on treating authorization, event authority, revisions, and provenance as product requirements rather than backend details.

The decisive next move is the secured CER vertical slice. It directly resolves the absence of a learner artifact in **#40**, establishes the typed controls required by **#41**, supplies trustworthy evidence for the **#44** acceptance journey, creates a place to safely contain and later govern **#42** diagnostics, and avoids overstating the current value of **#43**’s graph until it supports a bounded teacher decision. This sequence makes the earliest release useful under provider failure and defensible under review.
